Beleeg is league software for amateur sports — schedules, scoring, standings, brackets, payments, and messaging in one place. Its copilot, lebrAIn, can actually do the work: 43 real actions, each one prepared, previewed, and applied only after a person confirms. 01

The problem

Most amateur leagues are run by a volunteer — a commissioner, a bar owner, a club captain — on a spreadsheet, a group text, and whatever payment app people already have. The work is small and constant: move a game, fix a score, chase the team that hasn’t paid, email a division. Existing tools make them learn a product. Beleeg is built so they can just say what they want, and so that saying it can never quietly change anything they didn’t mean to.

The product

A React web app and an Expo mobile app over one shared TypeScript core — scoring, standings, the schedule generator, and the AI action registry are written once and used by both.

Run the season

A nine-step setup, schedule generation, lineups, live scoring, standings with configurable tiebreakers, playoffs, and tournament brackets.

Everyone gets their view

Home pages shaped for admins, captains, players, fans, media, and referees, plus public pages for every league, team, and organization.

Money moves correctly

Registrations, team dues, tournament entries, stores, and referee payouts through Stripe Connect, landing in the organizer’s own account.

Messages that arrive once

Email, SMS, and push through one queue with idempotency keys, a retry ladder, and a single policy for quiet hours and preferences.

Your own domain

Organizations can white-label Beleeg on their own domain; the app resolves which organization a request belongs to from the host it arrives on.

Moving a real league in

An idempotent import took a live league from its old Firestore app into Beleeg’s Postgres — deterministic IDs, so it can be re-run safely.

03

An AI that asks before it acts

lebrAIn is docked on every signed-in page. It reads a pre-computed brief of the league, accepts text, photos, and voice, and runs on Claude with at most three model calls per turn. What makes it safe to point at real data is the path every change has to take:

Ask Plain language

“It’s pouring — postpone tonight’s games.” The model can only choose from actions the registry exposes for this page and this person.

Check Server-side roles

Every action declares the roles allowed to take it, and the server filters on the caller’s real roles — never on what the client claims. A player can’t reschedule the league by asking nicely.

Prepare Nothing has changed yet

The action returns a plain summary, a preview of exactly what will change, and a ticket that expires in ten minutes. A stale approval is refused.

Confirm A person taps yes

Only the confirm step writes — and for actions that send email or open a Stripe checkout, it performs the delivery and reports what actually happened.

“Tell me what to do and I’ll line it up — you confirm before anything goes out.”

04

The same rules for everyone else’s AI

Beleeg ships an MCP server, so an organizer can run the league from Claude, Cursor, or any assistant that speaks the protocol. It is generated from the same registry as lebrAIn — one prepare tool per action, one shared confirm tool — so an outside model gets no path around the preview, the role check, or the person. It runs over stdio or stateless streamable HTTP, and assistants authenticate with scoped tokens that expire in thirty days.

05

Multi-tenant by default

Organizations own leagues, leagues own seasons, and permissions inherit down that tree. The database is default-deny: application data is reached through security-definer functions that check the caller, and audit scripts read the live schema to prove every one of those functions authenticates and every write stays inside its tenant. The schema is 136 migrations deep; the backend is Supabase Postgres plus 47 Deno edge functions.

06

Verified, not assumed

An agent that writes to real leagues has to be tested like one:

  • 300+ assertions on the write protocol run on every push: approval, scope, delivery state, and stale approvals, played out by five fake users — including the organizer of a second league, to prove cross-tenant requests fail. The whole suite runs in one transaction and rolls back.
  • The MCP server is tested end to end over real streamable HTTP, and 400+ Playwright tests cover the web app.
  • Budgets that only tighten: the entry bundle has a size cap that may be lowered but never raised, and lint findings may fall but never rise.
  • Honest copy is enforced: a linter fails on any user-visible promise of a feature that isn’t built, like “coming soon.”
  • Model evaluations can’t go stale: the demo league’s calendar moves every day, so each question’s expected answer is computed from the database at run time instead of being written down.
07

How it was built

Solo, in four months — 832 commits from the first scaffold to a live product with payments, mobile, an AI copilot, and an MCP server. The same way as everything else here: fleets of coding agents doing research, implementation, and adversarial review in parallel, with the verification gates above deciding what ships.
